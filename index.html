How it works

Connected in minutes, controlled from one dashboard

You decide when scans run. The work happens on GitHub's runners in your repository, and the results come back to TrustScan.

Connect GitHub

Install the TrustScan app on your account or organisation and choose the repositories it may scan.

Choose when to scan

On demand, on every pull request, on every push, or nightly at the hour you pick.

Scans run in your Actions

One small managed workflow file starts each scan on a GitHub-hosted runner. Your code is read there.

Review in one place

De-duplicated findings, triage that later scans respect, branch comparison and exports.

Security of the scan flow

Only a scan TrustScan started can run

The workflow file in your repository carries no secrets and no logic. Each run has to prove who it is before it gets anything.

  1. 1

    A one-time ticketTrustScan

    Every scan you start or schedule carries a random ticket, used once and bound to the first run that redeems it.

  2. 2

    GitHub's signed identityGitHub

    The run presents GitHub's signed token: which repository, which workflow, what started it, and that the runner is GitHub-hosted.

  3. 3

    Checked, then releasedTrustScan

    Only when every check passes does the run receive the key to TrustScan's encrypted, signed engine.

  4. 4

    Sealed resultsYour runner

    Results are encrypted to TrustScan's key before upload, and accepted only from the run the ticket was bound to.

The platform

Invite-only Google sign-in. Organisations with admin, member and viewer roles. Sessions stored as hashes and never put in URLs. A strict Content Security Policy on every page.

Built for the way teams ship

From the pull request to the audit trail

Pull-request checks

A TrustScan check on every pull request that fails only on findings the change adds, at the severity you choose.

Findings tracked across scans

New, still open or fixed: each finding keeps its identity, and a person's decision is never overwritten by a later scan.

Governed exceptions

Accepting a risk needs a reason and a VEX justification, a second approver for high and critical, and it always expires.

Branch comparison and policy gate

See what a branch adds, fixes or leaves unchanged. Each policy rule can block, warn or only report.

SBOM and SARIF exports

CycloneDX and SPDX 2.3 inventories, and SARIF 2.1.0 for GitHub code scanning and other tools.

Your editor and AI assistants

Connect Claude, Cursor, VS Code and other MCP tools to list findings, check a policy result or start a scan.

Your data

Your code stays on the runner unless you choose the code graph

Only the code graph keeps a copy of your source on TrustScan's servers, and only after an administrator in your organisation accepts a notice that says so.

Static analysis

Your code is read on the GitHub-hosted runner. Only encrypted results leave it.

Kept: findings, with the scan

Supply chain

Reads your dependency and lock files. Resolution runs in your Actions, sealed the same way.

Kept: the resolution artifact, 7 days in your Actions

Code graph

A copy of the repository is analysed on TrustScan's servers; parts of the code go to an AI model provider to check findings.

Kept: copy deleted within 24 hours; graph at most 30 days
